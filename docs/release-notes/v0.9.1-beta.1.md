# v0.9.1-beta.1: add the NVML symbols the Go-side jit-cdi enumeration needs

Changes since `v0.9.0`.

## Symptom: exit 127 on any per-GPU container

`nvidia-container-toolkit` >= 1.19 binds NVML through go-nvml as direct
cgo C symbols; the toolkit binaries carry all ~428 `nvml*` calls as
undefined dynamic symbols, resolved lazily on first use. When the stub
does not export one, the dynamic linker terminates the process before
any Go error handling:

```text
docker: Error response from daemon: ... OCI runtime create failed:
nvidia-container-runtime did not terminate successfully: exit status 127

nvidia-container-runtime: symbol lookup error: nvidia-container-runtime:
undefined symbol: nvmlDeviceIsMigDeviceHandle
```

No panic, no log, no stack trace. Every "run this specific GPU" path was
affected — `docker run --runtime=nvidia -e NVIDIA_VISIBLE_DEVICES=0` and
`nvidia-ctk cdi generate --device 0` — while `NVIDIA_VISIBLE_DEVICES=all`
and the C-side `nvidia-container-cli` chain kept working, which made the
failure easy to misattribute.

## fake NVML: two symbols close the enumeration gap

### [fake_nvml.c](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.1-beta.1/fake_nvml.c) ([c303d77])

- `nvmlDeviceIsMigDeviceHandle` — called unconditionally on the per-ID
  enumeration entry (`pkg/nvcdi/lib-nvml.go`) before any MIG decision.
  Always reports `isMigDevice = 0` with `NVML_SUCCESS`, consistent with
  the fake T4's no-MIG setting (`GetMaxMigDeviceCount` 0,
  `GetMigCapability` not-capable, `GetMigMode` DISABLED).
- `nvmlDeviceGetIndex` — called on the full-GPU spec generator
  (`pkg/nvcdi/full-gpu-nvml.go`). Returns the `fakeGpu_t` index field,
  mirroring `nvmlDeviceGetMinorNumber`; the implementation deliberately
  does not cast the handle pointer to an index.

Both functions NULL-check `device` and the output pointer (stricter than
the older device getters, whose NULL-device path would fault) and
return `NVML_ERROR_UNINITIALIZED` before `nvmlInit`.

## Self-checks against the next silent gap

### [check-nvml-symbols.sh](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.1-beta.1/check-nvml-symbols.sh) / [test_nvml_consistency.c](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.1-beta.1/test_nvml_consistency.c) ([c303d77], [190179a])

- `make check-nvml-symbols` diffs the NVML undefined-symbol set of the
  installed `nvidia-container-runtime` / `nvidia-ctk` against the stub's
  export table. A missing symbol on the nvcdi device-enumeration path
  fails; the ~390 other missing symbols are informational. The stub is
  resolved from the native-architecture `ldconfig` entry (a compat32
  entry is the real 32-bit driver and would pass trivially).
- `make test-nvml` links the built stub into a small C harness asserting
  the new semantics (always 0, index equal to `GetMinorNumber` and the
  `/dev/nvidiaN` node, stability across calls, and
  `GetHandleByIndex(GetIndex(h))` UUID round-trip).

## Validation

In-place upgrade from v0.9.0-beta.1 in the
`ghcr.io/ctrsploit/nvidia-container-toolkit-v1.20.2` environment
(kernel 6.8.0-71-generic, toolkit 1.20.2-1); module reloaded via
`rmmod nvidia && modprobe nvidia`, `modinfo` reports
`version: 0.9.1-beta.1-fake` ([78d81c2]):

- `docker run --rm --runtime=nvidia -e NVIDIA_VISIBLE_DEVICES=0
  ubuntu:22.04 true` — exit 0 (was 127);
- same with a `busybox` shell — exit 0, `/dev/nvidia0` present, no
  `nvidia-mps` in `/proc/self/mountinfo`;
- `nvidia-ctk cdi generate --device 0` — exit 0, spec contains the
  `name: "0"` device entry (was 127, no output file);
- `NVIDIA_VISIBLE_DEVICES=all` — exit 0 (regression);
- `nvidia-container-cli info` — prints NVRM/CUDA versions (regression);
- `make check-nvml-symbols` — PASS, no reachable symbol missing;
- `make test-nvml` — PASS.
