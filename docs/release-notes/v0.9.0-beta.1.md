# v0.9.0-beta.1: register the kernel module as 'nvidia' for nvidia-cdi-refresh compatibility

Changes since `v0.8.3`.

## Breaking change: module renamed to `nvidia`

The kernel module is now built, installed and loaded under the name
`nvidia` (was `fake_nvidia_driver`): `lsmod` shows `nvidia`, and the
load command is `modprobe nvidia`. `make install` automatically removes
stale v0.8.3 artifacts (`fake_nvidia_driver.ko` and its
`/etc/modules-load.d` conf), so an in-place upgrade just works; `make
uninstall` cleans both generations.

To keep the v0.8.3 name, build and install with `make
MODULE_NAME=fake_nvidia_driver`.

`modinfo nvidia` remains unambiguous: `version: 0.9.0-beta.1-fake`, a
MODULE_DESCRIPTION that states this is a fake registered under the name
'nvidia', and the `FAKE_NVIDIA:` dmesg prefix is kept.

## Kernel module identity: nvidia-cdi-refresh compatibility

### [Makefile](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.0-beta.1/Makefile) / [fake_nvidia_driver.c](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.0-beta.1/fake_nvidia_driver.c) ([a47b21d])

`nvidia-container-toolkit` >= 1.17.8 ships an `nvidia-cdi-refresh`
mechanism that auto-generates the CDI spec at boot and before the
container engines start. It decides "this host has an NVIDIA driver"
from two kernel-module identity faces:

1. a udev rule `ACTION=="add", SUBSYSTEM=="module",
   KERNEL=="nvidia|nvidia_current"` that pulls in
   `nvidia-cdi-refresh.service`;
2. the service's `ExecCondition` grepping `/(nvidia|nvidia-current)[.]ko`
   in `/lib/modules/$(uname -r)/modules.dep`.

With the module named `fake_nvidia_driver` neither face matched: the
ExecCondition failed on every boot and `/var/run/cdi/nvidia.yaml` was
never generated — `docker run --runtime=nvidia --device
nvidia.com/gpu=all` only worked after a manual `nvidia-ctk cdi
generate`. Renaming the module to `nvidia` satisfies both faces at once
(the kernel module name is the .ko base name).

Details:

- `MODULE_NAME ?= nvidia` with a branched kbuild mapping
  (`obj-m += $(MODULE_NAME).o` plus `$(MODULE_NAME)-y :=
  fake_nvidia_driver.o`); the source file keeps its name. The branch is
  required: a one-liner `obj-m` plus `-y` self-references for
  `MODULE_NAME=fake_nvidia_driver` and kbuild rejects it.
- `make install` now fails loudly when `depmod` fails (dropped
  `|| true`). `modules.dep` is load-bearing for the ExecCondition; a
  silent `depmod` failure reproduces the exact boot symptom this release
  fixes.

## fake NVML: `nvidia-smi -L` now works

### [fake_nvml.c](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.0-beta.1/fake_nvml.c) ([a13f670])

`nvidia-cdi-refresh.service` runs `nvidia-smi -L` as its first
ExecStart; with the v0.8.3 stub the real `nvidia-smi` (575.57.08
userspace) aborted with `Failed to initialize NVML: Function Not Found`,
which would have put the unit in a 5-restart loop at boot.

Four symbols close the gap (identified empirically with a bulk-stub
probe over all 254 missing symbols; the `-L` path calls nothing beyond
these and the already-exported APIs):

- `nvmlInitWithFlags` — the real nvidia-smi enters NVML through this
  entry point, *not* `nvmlInit`/`nvmlInit_v2`;
- `nvmlInternalGetExportTable` — must return `NVML_SUCCESS` with a valid
  pointer (a zero-filled static buffer); an error return aborts right
  after init with `Mismatch in versions between nvidia-smi and NVML`;
- `nvmlSystemGetNVMLVersion`, `nvmlSystemGetCudaDriverVersion_v2` —
  version queries (`nvidia-smi --version`).

## Device-node ordering at boot

### [fake-nvidia-device.service](https://github.com/ssst0n3/fake-nvidia/blob/v0.9.0-beta.1/fake-nvidia-device.service) ([2ccf785])

Renaming the module means `nvidia-cdi-refresh.service` is now pulled in
early at boot (udev module-add event). The node-creation service
previously ordered `After=multi-user.target`, i.e. *after* the first CDI
generation — the auto-generated spec would have lacked the per-GPU
`/dev/nvidiaN` entries with no self-heal (the module add event fires
once). It now orders `After=systemd-modules-load.service` and
`Before=nvidia-cdi-refresh.service`. Ordering against a unit that does
not exist (toolkit not installed) is silently ignored by systemd.

## Validation

Verified in the `ghcr.io/ctrsploit/nvidia-container-toolkit-v1.20.1:ctr_v0.1.0`
environment (Ubuntu 24.04, kernel 6.8.0-71-generic, toolkit 1.20.1-1,
Docker 28.2.0,
`.run` userspace 575.57.08), as an in-place upgrade from v0.8.3 followed
by a fresh boot:

- `/var/run/cdi/nvidia.yaml` auto-generated at boot; `nvidia-ctk cdi
  list` shows 9 devices (4 index + 4 UUID + all);
- `nvidia-cdi-refresh.service` completes (`ExecCondition` 0, no restart
  loop);
- `docker run --runtime=nvidia --device nvidia.com/gpu=all` works with
  no manual generate (all six device nodes in the container); legacy
  `--gpus=all` unchanged;
- `nvidia-smi -L` exits 0 listing 4 GPUs;
- module reload (`rmmod nvidia && modprobe nvidia`) re-triggers the
  refresh via the udev add event;
- `make MODULE_NAME=fake_nvidia_driver` round-trips back to the v0.8.3
  name and gate behavior.
